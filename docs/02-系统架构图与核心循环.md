# 3D 烹饪经营游戏 · 系统架构图与核心循环拆解

> 角色：全栈开发 + 高级开发工程师 ｜ 阶段：顶层架构设计（不写代码，定选型与分层）

---

## 1. 引擎与框架选型（结论先行）

| 维度 | 选型 | 理由 |
| --- | --- | --- |
| 渲染 | **Three.js (r160+)** | 生态最大、控制最细，自定义渲染管线自由；社区资源（glTF、后处理、粒子）齐全 |
| 物理（起步） | **cannon-es** | 活跃维护分支，**不是已停更的 Cannon.js**（原版最后提交 2015 年，直接否决）。API 兼容，切菜/颠勺/煎炸刚体需求覆盖得住 |
| 物理（性能档） | **Rapier (Rust/WASM)** | 当同屏刚体 >200 或需确定性同步时切换，性能数倍于 cannon-es，内存可控 |
| 构建 | **Vite + TypeScript** | 快启动、强类型、tree-shaking，适合中大型游戏工程 |
| 3D 渲染方式 | **命令式（不套 React 渲染 3D）** | 避免 Reconciler 开销，3D 用命令式更可控；HUD 用 DOM/CSS，必要时 React 只管 HUD 这棵独立 DOM 树 |
| 备选渲染 | Babylon.js | 内置物理/Inspector/全家桶，但首包更大、自定义自由度略低，不作为主选 |

**一句话**：Three.js 渲染 + cannon-es 物理起步，物理热点迁 Rapier；Vite + TS 工程化，3D 走命令式、HUD 走 DOM。

## 2. 系统架构分层

```
┌─────────────────────────────────────────────────────────────┐
│  表现层 (Presentation)                                        │
│  Three.js 场景渲染 · 粒子/锅气/油烟 · 后处理 · DOM HUD 浮层    │
└───────────────────────────┬─────────────────────────────────┘
                            │  命令 / 事件总线
┌───────────────────────────┴─────────────────────────────────┐
│  游戏逻辑层 (Game Logic)                                     │
│  核心循环状态机 · 规则判定(火候/QTE/定价) · 系统调度(ECS/模块) │
└───────────────────────────┬─────────────────────────────────┘
                            │  服务调用
┌───────────────────────────┴─────────────────────────────────┐
│  系统服务层 (Services)                                       │
│  经济系统 · 顾客AI(寻路+耐心) · 库存状态机 · 物理世界         │
│  · 事件/Roguelike(天气/评论家/短缺) · 存档                    │
└───────────────────────────┬─────────────────────────────────┘
                            │  读写
┌───────────────────────────┴─────────────────────────────────┐
│  数据层 (Data)                                               │
│  配置表(JSON/TS) · 本地存档(IndexedDB) · 云端存档(可选)       │
└─────────────────────────────────────────────────────────────┘
```

- **表现层** 只负责"画"和"收输入"，不含规则。
- **游戏逻辑层** 是唯一裁决者：火候算不算完美、定价赚不赚钱、顾客走不走，都在这里定。
- **系统服务层** 是无状态/弱状态服务，可独立单测（经济、AI、物理各自解耦）。
- **数据层** 配置与存档分离，配置走代码内 JSON，存档走 IndexedDB，云端仅做跨设备同步。

## 3. 核心循环拆解

营业日状态机：`采购 → 开张 → 烹饪(QTE) → 定价售卖 → 升级/随机事件 → 打烊结算 → 次日`。

### 3.1 采购（供应链）
- 输入：市场实时价（随机波动）、当前现金。
- 系统：经济系统给出低价信号，玩家低买；库存状态机记录保质期与存量。
- 反馈：买贵了顾客吐槽"这菜比金价还贵"，买便宜了弹"捡漏成功"。

### 3.2 烹饪（3D 物理 + QTE）—— 核心爽点
- 输入：鼠标/手柄切、颠、煎、炸；火候条 QTE 点击。
- 系统：物理世界跑刚体碰撞（食材飞溅、锅气粒子），逻辑层按火候值 + 甜点区 + QTE 时机判定品质。
- 反馈：连击、锅气、焦糊晕影（见 UI 文档 §5）。

### 3.3 定价售卖
- 输入：玩家给每道菜定价；系统按顾客口味偏好 + 当前声誉 + 行情给成交概率。
- 系统：经济系统结算金币与声誉，定价过高掉口碑、过低亏本。
- 反馈：顾客表情（⭐ 极品 / 🤬 暴走）、金币飞入。

### 3.4 升级 / 随机事件（Roguelike）
- 升级：天赋树（切菜速度+20%、解锁菜谱）+ 餐厅扩建 + 装修。
- 事件：每日随机天气、随机美食评论家、突发食材短缺；影响客流、难度、价格。
- 系统：事件系统按权重抽取，注入经济/AI 参数。

### 3.5 打烊结算 → 次日
- 系统：结算当日利润、声誉、员工工资、卫生检查。
- 反馈：日报卡片（赚/赔/翻车点），引导次日策略。

## 4. 技术栈对照（给团队的硬约束）

| 项 | 选用 | 备选 | 何时切 |
| --- | --- | --- | --- |
| 渲染 | Three.js | Babylon.js | 需要开箱全家桶且不在意首包时 |
| 物理 | cannon-es | Rapier | 刚体 >200 / 需确定性 |
| 语言 | TypeScript | — | 强制，不写 any 泛滥 |
| 构建 | Vite | esbuild 直跑 | 不换 |
| 状态 | 自研模块/ECS | 引入 RxJS | 事件多到失控再评估 |
| 存档 | IndexedDB | localStorage | 存档 >5MB 必须用 IndexedDB |
| 资源 | glTF + Draco + KTX2 | — | 模型必 Draco，纹理必 KTX2 |

## 5. 风险与对策（先说清楚）

- **cannon-es 性能上限**：单世界刚体别超 150，超了迁 Rapier，别硬扛。
- **3D + React 混用卡顿**：3D 永远命令式，React 只碰 HUD DOM，禁止在 render 里 new 对象。
- **存档损坏**：写入用事务 + 版本号，读档失败回退上一快照，不静默丢档。
- **首屏过大**：资源分包 + 流式加载，启动 ≤3s，详见性能规范文档。
