# 第五阶段设计记录 · 采购阶段与食材价格波动

> 目标：填补中循环里**唯一没填的环** —— 采购。
> 在此之前，食材成本是 `config.ts` 里的常量，玩家对"买什么、买多少"没有任何决策权，
> 于是「采购 → 烹饪 → 定价 → 升级」这条链上，采购只是个空转的状态。
> 产出日期：2026-09-19 ｜ 代码提交：见 `git log`（dev 分支）

---

## 1. 这一阶段解决什么

| 问题（改前） | 决策（改后） |
| --- | --- |
| 成本是常量，与玩家行为无关 | 成本 = **当日买进价**，每天 ±20% 浮动 |
| 采购阶段在状态机里空转 | 采购阶段有真实内容：看行情、进货、决定主推 |
| 一份料对应一锅菜，做完就换阶段 | 库存制：买 N 份就能连做 N 锅，料尽才收尾 |
| 钱亏光 = 卡死 | 破产保护：钱不够买料**且**零库存 → 免费发最便宜的料 |

一句话：**从"这是成本"变成"这是我花 8 块还是 10 块买的"**。
同一道菜、同一档位，只因进价不同，净利就差一截 —— 这才是"低买高卖"能成立的前提。

## 2. 状态机接线：采购 → 烹饪

原有状态机顺序未改，仍是 `采购 → 烹饪 → 定价 → 升级/事件 → 打烊 → 次日`，
变化在于**转移的触发条件不再是"时间到"，而是"业务条件满足"**。

| 转移 | 触发事件 | 前置条件（不满足则拒绝，且不推进状态机） |
| --- | --- | --- |
| 采购 → 烹饪 | `procurement:done` | 至少 1 份库存 |
| 烹饪 → 烹饪 | `potato:inPot` | 当前在该阶段 + 该食材有库存 |
| 烹饪 → 定价 | `dish:cooked` 结算后 | **库存已耗尽**（否则留在烹饪继续做） |
| 定价 → 升级 → 打烊 → 次日采购 | `endDay()` | 固定 4 步，无回环 |

### 关键防呆：两道阶段闸门

1. **`CookingSystem`**：订阅 `phase:changed` 维护 `inCookingPhase`，非烹饪阶段 `start()` 直接 return。
   理由：玩家可能在采购阶段随手点到 3D 场景里的食材，若无闸门会直接跳进烹饪、把进货界面顶掉 —— 一次误触毁掉一轮决策。
2. **`DayController.onPotatoInPot`**：同样要求 `day.current === 'cooking'`，并先扣库存。
   理由：状态机不能被"物理层的一次点击"推动；必须有业务前置条件。

> 这两道闸门是**刻意的冗余**，与"HUD 与 DayController 各写一遍烹饪中不可升灶台"同理，属防呆设计，非重复代码。

## 3. 价格波动模型

```
delta  = (rand() * 2 - 1) * PRICE_SWING        // PRICE_SWING = 0.2 → delta ∈ [-0.2, +0.2]
price  = max(1, round(baseCost * (1 + delta)))  // 取整，且至少 1 元（杜绝 0 元购）
```

- **随机源可注入**：`new MarketSystem(rng)`。冒烟测试传 `() => 0.5` 得 delta = 0（价格恒等于基准成本），
  传 `() => 1` / `() => 0` 钉死上下限 —— 否则金额断言每次跑数都不同，回归测试就失去意义。
- **`delta` 字段是"实际涨跌幅"而非掷出的随机数**：因为价格做了取整，`delta` 由取整后的价格反算，
  所以可能略微超出 ±20%（如豆腐 6 → 7，实际 +16.7%）。这是有意的：UI 展示的是玩家真实看到的变化。
- **每日重掷，库存跨日保留**：昨天囤的便宜货今天还能用 —— 这是"囤货"决策能成立的前提。

### 价格区间（Lv1 家用灶，售价倍率 1.0）

| 食材 | 基准成本 | 最低(−20%) | 最高(+20%) | 售价 | 成本占售价 |
| --- | --- | --- | --- | --- | --- |
| 土豆 | 8 | 6 | 10 | 30 | 26.7% |
| 豆腐 | 6 | 5 | 7 | 24 | 25.0% |
| 和牛 | 34 | 27 | 41 | 90 | **37.8%** |

### 各价位下的单锅净利（连击 ×1、家用灶、完美出锅）

| 食材 | 便宜 | 基准 | 贵 | 净利波动（对基准） |
| --- | --- | --- | --- | --- |
| 土豆 | +24 | +22 | +20 | ±9.1% |
| 豆腐 | +19 | +18 | +17 | ±5.6% |
| 和牛 | +63 | +56 | +49 | **±12.5%** |

### 各价位下的焦糊净亏（含售价 ×0.8 赔付 + 全额成本）

| 食材 | 便宜 | 基准 | 贵 |
| --- | --- | --- | --- |
| 土豆 | −30 | −32 | −34 |
| 和牛 | −99 | −106 | **−113** |

### 开局资金 60 元的实际选择（这条决定了开局体验）

| 选择 | 能买几份 | 权衡 |
| --- | --- | --- |
| 全买豆腐 | 8~12 份 | 容错最高（甜区 26 宽、慢火），但单锅只赚 17~19 |
| 全买土豆 | 6~10 份 | 中性基准，单锅赚 20~24 |
| 买 1 份和牛 | 1~2 份 | **赌博**：完美赚 49~63，糊一次亏 99~113 → 直接破产 |

> 设计结论：和牛同时具备「窗口最窄（Lv1 下 0.4 秒）」与「成本占比最高（37.8%）」，
> 是双重的风险收益标的。这是有意的 —— 高技巧玩家用它拉开收益差，新手碰它就是破产。

## 4. 破产保护

判据（**两个条件同时满足**才算走投无路）：

```
coins < 最便宜食材的今日单价   AND   全部库存合计 == 0
```

- 只要还剩一份料，玩家就还能开工挣钱 → 不发救济。避免把"保守经营"误判成破产。
- 触发时免费发放 `BANKRUPTCY_RESCUE = 3` 份**最便宜的**食材（当前是豆腐）。
  只发最便宜的料 —— 救济是"让你能继续玩"，不是"奖励破产"。
- 实现为 `DayController.checkBankruptcy()` **公开方法**：每日开市自动调用，也便于验证与将来做"破产成就"。
- UI 会明确提示「资金见底，赊到豆腐 ×3 应急」，不让玩家以为钱自己变多了。

## 5. 核心设计决策：成本绑定"买进价"

`EconomySystem.settle(grade, ingredientId, unitCost?)` 新增第三个参数。

- 入锅时 `DayController` 从当日行情取价，快照为 `currentUnitCost`；
- 出锅结算时把它传给 `settle()`，`unitCost` 缺省才回退到 `config` 基准成本（供测试直接发事件用）；
- **为什么由外部传入而不是内部查表**：成本绑在"你什么时候买的"上。昨天囤的便宜货和今天追高买的贵料，
  做出同一道菜利润不同 —— 这正是采购决策的意义。若内部查 `config`，采购阶段就白做了。

同时金币入口收敛为三个方法，全部在 `EconomySystem` 内、且只能由 `DayController` 调用：

| 方法 | 用途 |
| --- | --- |
| `settle()` | 出餐结算（含成本扣减） |
| `spend(amount)` | 采购付款 / 灶台升级（不足则拒绝，余额永不为负） |
| `earn(amount)` | 采购退款 / 未来事件奖励 |

`MarketSystem` 依旧**零事件总线依赖**（与 `EconomySystem` 同源）：它只算账，
返回 `spent` 由 `DayController` 去扣钱。这样"金币唯一出口"的约束没有被采购打破。

## 6. 事件契约新增

| 事件 | 载荷 | 发出方 | 语义 |
| --- | --- | --- | --- |
| `market:open` | `{ day, quotes[] }` | DayController | 每日开市，广播全部行情（UI 据此渲染货架） |
| `market:buy` | `{ id, qty }` | HUD（请求） | 买入请求，够不够钱由 DayController 裁决 |
| `market:bought` | `{ id, name, qty, spent, ok, reason? }` | DayController（回执） | 成功/失败都发，UI 才能给反馈 |
| `stock:changed` | `{ id, stock, total }` | DayController | 库存变化（买入 / 出餐消耗 / 救济）统一在此刷新 |
| `bankruptcy:averted` | `{ ingredientName, granted }` | DayController | 破产保护触发 |
| `procurement:done` | `{}` | HUD（请求） | 采购结束 → 请求进入烹饪 |

**`coin:earned` 复用于采购扣款与升级扣款**（`net` 为负、`revenue`/`penalty` 为 0）。
UI 用 `revenue > 0 || penalty > 0` 区分"是否真正的出餐结算"，只在出餐时弹结算浮字 ——
否则每次进货都弹一次会刷屏。

## 7. 死循环排查（代码审查专项）

用户明确要求"确保事件总线不出现死循环"。逐条核验事件链的深度：

| 事件 | 处理器动作 | 会不会回环 |
| --- | --- | --- |
| `phase:changed(→procurement)` | `openMarket()` → 发 `market:open` / `stock:changed` / 可能 `bankruptcy:averted` | 否：这三个事件 DayController 自己都不订阅 |
| `market:buy` | `buy()` → 发 `market:bought` / `coin:earned` / `stock:changed` | 否：均非 DayController 的入边 |
| `procurement:done` | `advanceTo('cooking')` → 发 `phase:changed(cooking)` | 否：处理器只对 `to === 'procurement'` 有动作 |
| `potato:inPot` | 扣库存 → `advanceTo('cooking')` | 否：同上 |
| `dish:cooked` | `settle()` → 发 3 个结果事件 + `advanceTo('pricing')` | 否：`pricing` 不触发任何回环 |

**结论：所有事件链深度 ≤ 1，无环。**
并在冒烟测试第 12 节用"一次收尾恰好推进 4 个阶段且序列固定"把它钉死（见下）。

## 9. 本轮修掉的问题

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| **装配顺序错误**：`Hud` 在 `DayController` 之后创建 | `DayController` 构造即 `start()` 并广播 `market:open`，HUD 会漏掉开局行情，货架要等到第二天才出现 | `cook-main.ts` 重排：表现层先订阅，中枢最后创建 |

## 10. 待调项（进入下一轮）

1. **价格波动幅度偏小**：土豆 ±9.1% 的净利波动，玩家很难感知。可考虑放大到 ±30%，或加入"连续低价日"等趋势。
2. **无仓容上限**：理论上可以囤无限料，缺少"冰箱放不下"的约束。`MAX_STOCK_PER_ITEM` 已预留（当前 99）。
3. **无保质期 / 损耗**：囤货只有好处没有代价，"低买高卖"缺少风险面。
4. **采购阶段没有时间压力**：可以无限思考，与"极其杀时间"的目标不符。可考虑每日限时采购。
5. **和牛风险过高**：开局买 1 份和牛糊一次即破产（亏 106 vs 本金 60），可能劝退。需实机手感验证。
6. 质量分仍未参与结算（已算好，未用）。
7. 灶台升级不可逆（无退款/降级）。
