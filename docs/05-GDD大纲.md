## 1. 一句话

开一家小破馆子。买菜、看火、出锅、收钱。手一抖，一天白干。

**三句话定位**
- 极易上手：点土豆入锅，绿区点锅就出锅。
- 极难精通：绿区只有零点几秒，还得连击不断。
- 极其杀时间：一天亏光就想再来一天。

## 2. 核心循环

### 2.1 三圈嵌套

| 循环 | 时长 | 玩家在做什么 | 为什么再来一圈 |
| --- | --- | --- | --- |
| **微循环（一口菜）** | 3~5 秒 | 看火候条，掐点出锅 | "刚才就差一点点" |
| **中循环（一个营业日）** | 2~4 分钟 | 采购买菜 → 连续出锅 → 定价收钱 → 升级 | 今天净利为正就还想冲更高 |
| **宏循环（一局）** | 20~40 分钟 | 攒钱扩店、解锁菜谱、扛随机事件 | 新菜谱 = 新火候曲线 = 重新学 |

### 2.2 中循环流程（当前已跑通）

```
采购(procurement) → 烹饪(cooking) → 定价(pricing) → 升级/事件(upgrade) → 打烊(closing) → 次日
        ↑                                                                              │
        └────────────────────────────── 闭环 ────────────────────────────────────────┘
```

**每一环的"钩子"**
- **采购**：食材价格会波动，今天土豆便宜就该囤。
- **烹饪**：唯一的操作环节，也是唯一的爽点来源。**这里是全部紧张感的产地。**
- **定价**：标高了没人买，标低了白忙。看今天来了什么客人。
- **升级/事件**：灶台升级会让你更赚、也更难——这是本作的核心张力。
- **打烊**：结算。亏了就是亏了，没有读档。

## 3. 心流：紧张感从哪来

这是本作最要紧的设计，比美术重要一百倍。

### 3.1 紧张的三个来源

| 来源 | 机制 | 玩家心理 |
| --- | --- | --- |
| **时间压力** | 火候只涨不跌，甜区窗口 0.4~1.0 秒 | "来不及看了，手先动" |
| **损失厌恶** | 焦糊不只没收成，还倒赔食材钱 + 顾客怒 | "宁可生一点，别糊" |
| **连击包袱** | 连击越高，一次失手亏得越狠 | "这锅不敢快，但我又赶时间" |

> **关键取舍**：火候条必须**同时**给出三种信息——当前位置、安全区、危险区。少给任何一个，紧张感就变成瞎猜。这是 UI 的死线。

### 3.2 三档难度自选（玩家自己给自己上难度）

| 灶台 | 升温 | 甜区宽度 | 售价 | 体感 |
| --- | --- | --- | --- | --- |
| 家用灶 | 慢 | 宽 | ×1.0 | 练手，容错高 |
| 商用灶 | 中 | 略窄 | ×1.25 | 开始有压力 |
| 猛火灶 | 快 | 窄 | ×1.5 | 手速活 |
| 分子料理灶 | 极快 | 极窄 | ×1.8 | 不是人玩的，但有人就是要玩 |

**核心张力**：升级灶台=赚更多+难更多。想赚钱必须升，升了就打不过自己的手。玩家永远在"我够快了吗"的自我怀疑里循环。

食材同理：和牛贵、火快、窗口窄、糊一次赔到肉疼。

## 4. 爽感：从哪来

| 爽点 | 触发 | 反馈（必须同时给满） |
| --- | --- | --- |
| **完美出锅** | 甜区内点锅 | 金光爆开 + 金币飞入钱袋 + 屏幕震动 + 上行双音 + 连击弹字 |
| **连击滚钱** | 连续完美 | 倍率 ×1→×2→×3…，金币数跳涨，震动逐级加强（封顶防晕） |
| **最后一秒惊险** | 甜区边缘出锅 | 算完美，跟正中一样给满奖励。**鼓励赌，不惩罚勇** |
| **翻盘** | 亏到快破产时一锅和牛完美 | 一次赚回半天的钱 |

**负面反馈必须更响**
| 失误 | 反馈 |
| --- | --- |
| 生食/过火 | 连击归零 + 画面泛红 + 闷响 |
| 焦糊 | 连击归零 + 黑晕 + 重震 + 顾客怒 |

> **原则**：正反馈给"爽"，负反馈给"痛"。中间态（平淡的出餐）越少越好。玩家不该有"还行"的感觉。

## 5. 系统结构

### 5.1 四层架构（单向数据流，禁止回头）

```
┌─────────────────────────────────────────────────┐
│ 表现层  ui/ · audio/ · render/                   │
│ 只订阅事件，只管画/响/抖。不做任何规则判断。        │
└────────────────────┬────────────────────────────┘
                     │ 订阅结果事件
┌────────────────────▼────────────────────────────┐
│ 玩法层  game/CookingSystem · game/EconomySystem  │
│ 火候推进、档位判定、连击、金币。纯数据，绝不见 3D。 │
└────────────────────┬────────────────────────────┘
                     │ 发意图 / 收结果
┌────────────────────▼────────────────────────────┐
│ 核心层  core/EventBus · core/Ticker · core/StateMachine │
│ 事件总线、统一帧循环、通用状态机。不写业务。        │
└────────────────────┬────────────────────────────┘
                     │ 意图事件
┌────────────────────▼────────────────────────────┐
│ 物理层  render/PhysicsScene                      │
│ 只报告"玩家点了什么"，绝不判断"这该赚多少钱"。      │
└─────────────────────────────────────────────────┘
```

### 5.2 模块职责（谁管什么，一眼看清）

| 模块 | 管什么 | 绝不管什么 |
| --- | --- | --- |
| `PhysicsScene` | 3D 锅/土豆、物理碰撞、射线点击 | 火候、金币、连击 |
| `CookingSystem` | 火候推进、四档位判定、质量分 | 金币、库存、UI |
| `EconomySystem` | 连击、售价、成本、罚金、灶台等级 | 火候、3D、DOM |
| `DayController` | 把玩法事件接到营业日状态机，**统一结算** | 火候算法、渲染 |
| `BusinessDayMachine` | 营业日阶段流转 | 任何数值 |
| `Hud` / `Juice` / `AudioManager` | 显示、抖动、发声 | 一切规则 |

### 5.3 事件流（第四阶段定稿契约）

```
[点土豆]  PhysicsScene ──potato:cut / dish:prepared / potato:inPot──▶ CookingSystem
[入锅]    CookingSystem ──cooking:start / cooking:progress(含档位)──▶ Hud / PhysicsScene
[点锅]    PhysicsScene ──pot:clicked──▶ CookingSystem
[出锅]    CookingSystem ──dish:cooked{档位,质量,火候}──▶ DayController
[结算]    DayController ──▶ EconomySystem.settle() ──▶ combo:changed
                                                   └─▶ coin:earned
                                                   └─▶ customer:angry(焦糊时)
[表现]    Hud / Juice / Audio / PhysicsScene 订阅上述结果事件
```

**铁律三条**
1. `PhysicsScene` 只发意图，不判规则。
2. `CookingSystem` 只发 `dish:cooked`（带档位+质量），**不算钱**。
3. 金币只能由 `DayController` 结算。任何模块不得直接调用另一个模块。

## 6. 四档位定义（本阶段核心）

| 档位 | 火候 | 质量分 | 售价 | 连击 | 顾客 |
| --- | --- | --- | --- | --- | --- |
| 生食 raw | < 甜区下界 | 0~60 | ×0.2 | **归零** | 勉强收下，脸很臭 |
| 完美 perfect | 甜区区间内 | 100 | **×连击倍率** | **+1** | 眼睛发光 |
| 过火 over | 甜区上界 ~ 100 | 80~30 | 0，倒赔 | **归零** | 要求退钱 |
| 焦糊 burnt | ≥ 100（自动） | 0 | 0，重罚 | **归零** | **愤怒** |

> **过火与焦糊的区别**：过火是玩家主动出锅救回来（还能卖个价但也赔），焦糊是火候自己烧穿（血本无归）。前者是"止损"，后者是"事故"。

## 7. 本版不做（明确边界，防止发散）

| 不做 | 原因 |
| --- | --- |
| 精美 3D 模型 | 灰盒阶段，机制没定死之前美术全是浪费 |
| 顾客寻路 / 排队 AI | 下一步。先证明"看火候条"这件事本身好玩 |
| 食材市场价格波动 | 下一步。先有稳定成本基准，再谈波动 |
| 天赋树 / 多菜谱 | 下一步。现在只有 3 种食材试水 |
| 存档 | 机制定型后再做，否则存档结构要重写三遍 |
